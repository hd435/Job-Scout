# v0.9 — Scaling to 1,000+ employers

**Status:** Approved (2026-11-13)

## Objective

Grow Job-Scout progressively from ~110 to **1 000+ distinct employers** so that it discovers the
largest practical share of relevant UK early-career vacancies.

**North star: opportunity coverage** — the proportion of real UK graduate, internship, placement and
apprenticeship vacancies in the enabled role families that Job-Scout discovers. Employer count is a
supporting measure: an employer that never produces a match costs scan budget and adds nothing.

## Agreed product decisions (2026-11-13)

These are settled. Development work should not reopen them.

1. Opportunity coverage is the primary success measure; employer count is supporting.
2. Progressive employer expansion towards 1 000+ is approved.
3. **Workday expansion is approved**, with a reusable and appropriately bounded approach.
4. Matching scope extends to **engineering, science/R&D and supply chain** — no shadow trial required.
5. **Public-sector and aggregator expansion is on hold.** Government, NHS, universities and the
   aggregators they publish on are out of scope for this phase.
6. **Alerts stay unlimited.** No daily caps, no suppression by volume; `/digest` remains the way to
   review everything that matches.
7. **Keep the current Oracle deployment.** No new infrastructure, no paid services, no architecture
   redesign in anticipation of growth; capacity changes only when measurements demand them.
8. Newly added employers must never silently widen an existing user's saved employer scope.
9. Preserve notification reliability, duplicate prevention and the complete-scan safeguards.

Recorded as D-106 … D-112 in [decisions.md](../decisions.md).

## Measuring success

| Measure | What it answers | Target shape |
|---|---|---|
| **Opportunity coverage** | Share of roles in an independent UK early-career sample we monitor | Baseline 28 % (2026-11-13); rising |
| **Contributing employers** | Employers producing ≥1 match in 90 days | The number that matters; zero-contributors reported openly |
| Employer count | Catalogue size | Supporting only |
| Match precision | Share of a manual sample of alerts a human agrees with | Must not fall when families are added |
| Source health | Sources with a complete scan in 24 h; partial-scan rate series | Complete-first-scan is a gate; partial rate must not creep |
| Capacity | p50/p95 pass duration vs cadence; request budget consumed per pass; DB growth; Telegram p95 reply latency | Headroom inside cadence |

Coverage is reported against **two** independently sourced samples so the number cannot be tuned to
one list. Public-sector roles are excluded from the coverage ratio while decision 5 stands, and that
exclusion is stated wherever the figure is quoted.

## Discovery and validation

Three lead engines feed one committed registry:

1. **Vacancy-first** — start from real postings, trace to the employer's own board. Highest precision.
2. **Curated recruiter populations** — graduate-employer rankings, professional-body and sector
   association member lists. Reaches sectors the vacancy lists under-represent.
3. **Platform inventory** — enumerate named tenants of platforms we can read, then gate each by probe.

**The registry is committed, not incidental.** One row per employer: normalised name, domain,
platform/tenant/site, status (`candidate`, `added`, `rejected(reason)`, `blocked(platform)`,
`deferred`) and the evidence behind it. Probe results write into it. Today that knowledge lives in
prose and gitignored files, which is how research gets repeated.

**The enrolment gate (D-100, unchanged):** a complete board, ≥1 UK role, and ≥1 UK role in an
*enabled* family; plus `validate --live-only` PASS and a complete, silent first scan.

## Platform strategy

**Workday is the growth engine** — 47 % of roles in the reference sample, and 5 of 78 identified
tenants are read today.

- Prefer **purpose-built early-career sites** (`intern_graduate`, `*_campus_careers`,
  `Graduate_careers`) over group boards: `mbda-uk` yields 73 graduate roles complete; a 731-role
  group board hits the page cap and never completes.
- For large group boards, narrow server-side (`search_text`, and facets) rather than by page cap.
- Per-tenant politeness is already possible because each tenant is its own host; add a per-tenant
  page cap and a longer cadence for large boards.
- A tenant is proven by one command before it is enabled, and re-proven when the platform changes.

**Secondary platforms in value order:** SuccessFactors, Taleo, Oracle HCM, iCIMS — each a go/no-go
on measured UK early-career volume. Recruitee, Teamtailor, SmartRecruiters and Rippling are
opportunistic: cheap, but small in this market.

## Matching scope extension

The engine already supports this without new abstractions: families map to title stems, a role may
belong to several, and `EXCLUDED_FAMILIES` routes conflicts to `needs_review` instead of alerting.

- New families: **engineering**, **science** (R&D), **supply_chain**.
- Commercial look-alikes (`sales engineer`, `support engineer`, …) are added to the exclusion list so
  they resolve to review, not alerts.
- Precision is measured on the ~481 stored `needs_review` rows before alerts are enabled, not argued.
- Existing users are unaffected: matching uses each user's **stored** family list, so a new family
  never widens an existing subscription. Users opt in through `/settings`.

## Phases

| Phase | Outcome | Depends on | Known-good when |
|---|---|---|---|
| **0. Growth safety** | Request budget per pass, scanning interleaved with polling, single next-due query, per-source digest invalidation, cadence tiers and jitter, per-source staleness in `service status` | — | 24 h soak with no budget refusals; pass well inside cadence; Telegram latency stays low |
| **1. Registry + pipeline** | Committed employer registry; lead ingest → probe → validate → catalogue file | 0 | Adding an employer is one command; no duplicated research |
| **2. Matching scope** | Engineering, science/R&D, supply chain live | 0 | Precision spot-check passes; existing user scopes provably unchanged |
| **3. Workday waves** | ~10 → ~25 → ~60 tenants, early-career sites first | 0, 2 | Every tenant complete, ≥1 UK family role, measured match per tenant |
| **4. Sector batches** | Engineering/defence, pharma/life sciences, insurance/banking, energy, consumer/FMCG, consulting/law | 1–3 | Coverage rises; contributing-employer ratio tracked |
| **5. Platform go/no-go** | SuccessFactors, Taleo, Oracle HCM, iCIMS assessed | 4 evidence | Written decision per platform |
| **6. Capacity review** | Only if measured: pass time, CPU, pacing saturation | 4 | Pass time under ~60 % of cadence, else rebalance cadence first |

Phases 1 and 2 run alongside 3's first wave. Phase 4 is a rolling loop, not a gate.

## Operational considerations

- **Capacity stays as it is.** The VM is `E2.1.Micro` (1/8 OCPU). Cadence tiers are a configuration
  lever and come before any capacity conversation.
- **Scan duration is the binding constraint, not storage.** 17 782 jobs / 127 MB / ~6 MB per day
  leaves years of boot volume; a sequential pass at 1 000 sources does not fit a 30-minute cadence
  without tiers.
- **Silent partial scans are the main reliability risk at scale.** A source that never completes
  never alerts, and nobody can eyeball 1 000 sources. Completeness per source is reported, not assumed.
- **Unlimited alerts are a product decision.** Volume per subscriber is observed and reported so the
  consequence is visible; it is not capped.
- **Deployment is unchanged.** Changes ship through `install.sh`; the store's own `verify.sh` remains
  the check. No live deployment change happens as part of development.
