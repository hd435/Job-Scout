# v0.6 — Scale out

**Status:** Approved 2026-10-24 · **Owner:** Product Owner · **Iteration of:** [prd.md](../prd.md)
**Predecessor:** v0.5, delivered 2026-10-24 — six researched employers live, configurable scope,
20 current matches under the operator's pinned London scope
**Successor (not this iteration):** expansion to ~100 employers as operational work

This file is the reference for the iteration. Once delivered it is not rewritten.

---

## 1. Why this iteration exists

v0.5 made scope and source shape configuration. It left three things that only matter at scale:

- The six employers live inside `config.py`. Adding the seventh is a Python change, and adding
  ninety is ninety of them.
- Each scan paces itself, but nothing paces the *host*. At six sources that is invisible; at a
  hundred, two sources on one ATS tenant can be scanned back to back in the same pass, and a
  sitemap source's 400-page crawl can overlap another source's crawl on the same domain.
- `status` prints a block per source and nothing records whether a source was ever *validated*.
  At six sources the operator can hold that in their head; at a hundred they cannot.

## 2. Outcome

> Adding an employer is a file, pacing is a property of the host rather than of the adapter, and
> one command shows the state of a hundred sources and whether expanded coverage is finding
> anything worth reading.

## 3. Scope

### In scope

1. **Catalogue.** Employers live in TOML files, one per employer, in a `catalogue/` directory.
   The package ships six; an operator points at their own directory instead, and narrows the
   result with a `disable` list, so local choices stay local without editing catalogue files.
2. **Host pacing.** One pacer per process, shared by every source: a minimum interval per host,
   optional per-host overrides, and a hard per-process request budget so a misconfiguration
   cannot turn one pass into a crawl.
3. **Operational visibility.** `status --brief` and a summarised `sources list` with a validation
   record, so "never validated", "failing" and "finding nothing" are distinguishable at a glance.
4. **Measurement.** The report states, per source, how many roles it contributes and how many
   matched, so coverage can be judged rather than assumed.
5. **Keeping the beta.** The six-source beta keeps running with its local pinned-London scope
   throughout; the new machinery is developed and tested around it.

### Out of scope

- Any employer beyond the six researched ones. Expansion is the Product Owner's operational work
  with the machinery this iteration delivers.
- A web UI, hosted service, or accounts.
- Alert-volume policy (D-070 stays deferred).
- Rewriting the adapters: the four supported shapes and their option contracts are unchanged.
- Adding an adapter for a new *kind* of access. A site that needs a new parser still needs code,
  and both the README and `configuration.md` keep saying so.

## 4. Decisions applied

| Topic | Decision |
|---|---|
| Catalogue layout and precedence | bundled catalogue, or an operator catalogue directory instead; `[[sources]]` in the config file still replaces the list entirely (D-081) |
| Disabling without editing files | `[jobscout] disable = ["id", …]` in the local config (D-081) |
| Pacing | process-wide per-host interval plus a per-process request budget (D-082) |
| Validation record | `validate` writes a marker under `data/validation/`; `sources list` reads it (D-083) |
| Status at scale | `status --brief`; `sources list` summarises and stays one line per source (D-084) |
| Coverage measurement | per-source roles, matches and review counts in the report (D-085) |

## 6. The expansion process this enables

Once delivered, growing the catalogue is a batch loop rather than a development cycle:

1. Pick a batch of employers (10–15) whose careers sites use one of the four supported shapes.
2. For each, write one catalogue file and run `config validate` (offline).
3. Run `validate --source <id> --confirm-live` — bounded, and it records the result.
4. Take one scan by hand, review `summary --current`, then let the schedule pick it up.
5. Once per batch, read `report` and drop sources that contribute nothing.

The runbook carries this as a procedure; this iteration delivers the pieces it needs.

## 7. Exit state

v0.6 is delivered when V06-1…V06-8 pass, the six-source beta is still running on the operator's
machine, and the documentation map is accurate. The next work is the expansion itself.
