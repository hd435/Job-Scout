# v0.5 — Configurable scope

**Status:** Approved 2026-10-24 · **Owner:** Product Owner · **Iteration of:** [prd.md](../prd.md)
**Predecessor:** the two-source personal beta (`lloyds_graduate`, `monzo`) running on the
operator's machine since 2026-10-23
**Successor (not this iteration):** v0.6 scale-out to ~100 employers as operational work

This file is the reference for the iteration: what it delivers, in what order, and how we will
know it is done. Once delivered it is not rewritten — see [docs/README.md](../README.md).

---

## 1. Why this iteration exists

The beta proved the machinery end to end: parse → match → dedup → Telegram, on two live sources.
It also exposed the limiting factor. Today a user can choose *which employers* to poll, but not
*what work, at what seniority, in which cities* — those are Python constants. That makes the
product a personal tool for one person rather than a product a friend could clone, and it blocks
the coverage goal:

- Coverage goal: **~100 employers**, with continuous expansion as the main ongoing work.
- Expansion must therefore be configuration and operations, never a code change.
- Until scope is configurable, adding employers only multiplies one person's preferences.

The observed supply makes the case concrete: two live employers produced 105 roles and 17 matches,
but Monzo contributed **zero** graduate roles and no new role arrived in 13 hours. Coverage, not
matching, is what limits usefulness.

## 2. Outcome

> Any user can define their own job-search scope in configuration, any employer can be added
> without touching Python, and the six researched employers run live — so that reaching ~100
> employers becomes routine operations rather than development.

## 4. Scope

### In scope

1. A preferences model covering role families, seniority, employment types, locations and title
   exclusions — with defaults that reproduce today's behaviour exactly.
2. Configuration-only support for adding an employer on Lever, Greenhouse, Workday, and any
   careers site publishing schema.org `JobPosting` JSON-LD behind a sitemap.
3. `validate` extended to any configured source, with a bounded budget inferred from adapter type.
4. The four researched-but-not-yet-enabled employers validated live and enabled, bringing the six
   researched employers to operational status.
5. Two small fixes: an undelivered failure notice is retried, and a non-JSON HTTP response is
   reported with its status and a bounded body snippet instead of a JSON parse error.
6. Documentation brought into line with the running product (PRD, README, roadmap, runbook).

### Out of scope

- Any employer beyond the six researched ones. Expansion to ~100 is **operations**, performed by
  the Product Owner with the machinery this iteration delivers.
- Batched or digest alerting, alert caps, quiet hours (D-070).
- A dashboard, web UI, hosted service, or accounts.
- Cross-source duplicate detection beyond the duplicate-employer guard.
- Process supervision beyond the existing Windows scheduled task.

## 5. Increments

Each increment ships independently and leaves the beta working throughout.

### 0.1 — Fixes and truthfulness

*Deliverables*

- Failure notice: when the previous outcome was `failed`, allow one retry on a later pass. Never
  retry `ambiguous` (D-024). Rationale: a single failed send currently silences the whole episode,
  and the most likely cause of that send failing is the outage being reported.
- Non-JSON response: report HTTP status plus a bounded body snippet, so an interception page is
  identifiable instead of surfacing `Expecting value: line 1 column 1`.
- Decisions D-066…D-072 recorded.
- Rewrite of the stale sections: PRD status, release definitions, AC-13/AC-19/AC-20; README
  current state and source table; runbook §3; roadmap release view.

*Exit criteria* — tests cover both retry and non-retry paths; every stale claim named in the
v0.5 review is corrected.

### 0.2 — Preferences model

*Deliverables*

- `[preferences]` schema (section 6) with defaults identical to current behaviour.
- Validation that names the offending key and value; unknown keys rejected.
- `jobscout config show` (effective settings, config path, rules version) and
  `jobscout config validate`.
- Match decisions record the preference fingerprint, so a decision can always be explained.

*Exit criteria* — a clone can change families, seniority, employment types, locations and
exclusions in configuration only; an invalid preference fails loudly at load.

### 0.3 — Source catalogue

*Deliverables*

- Config-only definitions for Lever (`site`), Greenhouse (`board`), Workday
  (`host`/`tenant`/`site`/`locale`).
- Generic sitemap source: `sitemap_urls`, `job_url_pattern`, `id_pattern`, optional
  `location_from` — replacing the in-code `wise`/`arm` profiles.
- `jobscout sources list` / `add` / `disable` operating on the local configuration file.
- Duplicate-employer guard: the same employer or the same job URL under two sources warns at load.
- `validate` for any configured source, with the request budget inferred from adapter type.

*Exit criteria* — a new employer of each supported access shape is added and validated with no
Python change; `sources list` shows every configured source with its adapter and state.

### 0.4 — Six researched employers live

*Deliverables*

- Live validation of Barclays, Wise, Arm (Palantir is already validated), each with a recorded
  bounded request count and result.
- All six researched employers enabled and baselining on the operator's machine.
- Runbook updated with the add-an-employer procedure that expansion will follow.

*Exit criteria* — six sources report complete scans; the add-an-employer procedure has been
executed once end to end without code changes.

## 6. Proposed configuration schema

Defaults reproduce today's behaviour. Everything below lives in the local config file (by default
`config.toml`, or any path passed with `--config`); none of it is committed.

```toml
[jobscout]
database = "data/jobscout.db"

[preferences]

# Which role families may alert. Unknown names are rejected.
role_families = ["data", "software", "quant", "finance", "consulting", "business_analysis"]

# Title qualifiers that exclude a role, matched before inclusion.
seniority_exclusions = [
  "senior", "snr", "sr", "lead", "principal", "staff",
  "head", "director", "vice president", "vp", "chief", "manager",
]

# Which employment types may alert. `unknown` never alerts.
# `experienced_hire` covers titles that ask for multiple years of experience.
employment_types = [
  "graduate_scheme", "internship", "placement", "apprenticeship", "entry_level_permanent",
]

# Extra exclusions, applied to titles after family matching.
title_exclusions = []

[preferences.locations]
# "pinned"         -> only the listed cities qualify
# "uk"             -> any UK location qualifies
# "uk_plus_pinned" -> any UK location qualifies, plus the listed cities outside the UK
mode = "uk"
cities = []            # e.g. ["London", "Manchester", "Edinburgh", "Leeds"]
remote_uk = true       # include roles explicitly remote within the UK
hybrid_uk = true       # include UK hybrid roles

[[sources]]
id = "lloyds_graduate"
employer = "Lloyds Banking Group"
adapter = "workday"
enabled = true
cadence_minutes = 30

[sources.options]
host = "lbg.wd3.myworkdayjobs.com"
tenant = "lbg"
site = "Graduate_careers"
locale = "en-US"
uk_employer = true

# A source added purely by configuration, with no Python change:
# [[sources]]
# id = "example_greenhouse"
# employer = "Example Ltd"
# adapter = "greenhouse"
# [sources.options]
# board = "example"
#
# [[sources]]
# id = "example_sitemap"
# employer = "Example Ltd"
# adapter = "sitemap_html"
# [sources.options]
# sitemap_urls = ["https://example.com/sitemap-jobs.xml"]
# job_url_pattern = "/careers/job/"
```

### 6.1 Employment-type classes

| Class | Recognised by | Alerts by default |
|---|---|---|
| `graduate_scheme` | graduate programme/scheme/pathway wording | yes |
| `internship` | intern, internship, summer analyst | yes |
| `placement` | industrial placement, placement year | yes |
| `apprenticeship` | apprentice, apprenticeship | yes |
| `entry_level_permanent` | entry-level/junior wording without a scheme label | yes |
| `experienced_hire` | explicit multi-year experience requests | **no** |
| `unknown` | nothing recognisable | **no** |

Classification uses the fields a source actually exposes (title, `timeType`, scheme wording,
description signals), so it is a documented heuristic, not a guarantee. `unknown` never alerting is
deliberate: silence is safer than noise, and `summary --current` still shows those roles for review.

### 6.2 Location semantics

Cities are resolved through the existing city knowledge with ambiguity handling preserved: a city
name that also exists abroad needs either an explicit country or a source marked `uk_employer`
(D-065). Pinning an ambiguous name is allowed; the resolution rule does not change.

The operator's operative mode for the beta is `pinned` (D-069); the shipped default remains `uk` so
a clone is not silently narrowed.

**Operator's pinned scope (confirmed 2026-10-24):** `cities = ["London"]` with UK remote included.
In config form:

```toml
[preferences.locations]
mode = "pinned"
cities = ["London"]
remote_uk = true
hybrid_uk = true   # a hybrid role that names London already qualifies by city
```

This means a Manchester-only or Edinburgh-only role does **not** alert for this operator, by
explicit choice. `summary --current` still lists those roles, so the choice stays reversible.

## 7. Acceptance criteria

| ID | Criterion |
|---|---|
| **V05-1** | A clone can change employers, role families, seniority, employment types, locations and title exclusions using configuration only; an invalid value is rejected naming the key. |
| **V05-2** | An employer on Lever, Greenhouse, Workday, or a JSON-LD careers site behind a sitemap is added with no Python change, and `sources list` shows it. |
| **V05-3** | `validate` works for any configured source and refuses to exceed its inferred budget before the extra request reaches the network. |
| **V05-4** | Six researched employers complete a scan on the operator's machine. |
| **V05-5** | A failure notice whose send failed is retried once; an `ambiguous` outcome is never retried; both covered by tests. |
| **V05-6** | A non-JSON response is reported with status and bounded body snippet, never as a bare parse error. |
| **V05-7** | PRD, README, roadmap, runbook and decision log agree with the running product, including the beta and the blanket access posture (D-066). |
| **V05-8** | Invariants preserved: silent baseline, complete-scan-only eligibility, no duplicate alerts, official links only, partial scans never closing roles, secrets out of Git and logs. |

## 8. Invariants that must not regress

1. The first complete scan of a source is silent; only later complete scans can alert.
2. A role first seen in a partial scan is not alert-eligible until a complete scan sees it.
3. At most one alert per `(chat, source job id)`; `sent` rows are never re-sent.
4. Ambiguous Telegram outcomes are recorded and never retried.
5. Closure requires two consecutive complete misses; partial and failed scans never contribute.
6. Every alert links to the official employer or ATS listing.
7. Secrets never enter Git or logs.
8. Tests and linters stay green; no live request is made without operator approval.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Preferences creep into a rules DSL | Declarative lists with documented defaults; no expressions, no scripting |
| Employment-type inference is out of reach for sources that expose no type | Documented heuristic; `unknown` never alerts; visible in `summary` |
| Narrowing locations hides roles the user wanted | `mode` is explicit; `summary --current` and `report` expose what was excluded |
| Adding employers by config silently mis-parses a new site | `validate` before enabling; a failed parse is visible; adapters report skips |
| Duplicate employer configured twice | Guard warns at load |
| Expansion outruns politeness | v0.6 owns per-host rate limiting; expansion here is limited to the six |

## 10. What this iteration deliberately does not deliver

- ~100 employers. It delivers the machinery; the list is the Product Owner's ongoing operational
  work (D-066).
- Alert-volume control at scale (D-070).
- Any supervision beyond the existing scheduled task.
- Sitemap support for sites that publish no JSON-LD — they remain unsupported rather than guessed.

## 11. Exit state

v0.5 is delivered when V05-1…V05-8 pass, the six researched employers are live on the operator's
machine, and the documentation map in [docs/README.md](../README.md) is accurate. The next
iteration (v0.6) covers scale: ~100 employers in batches, per-host politeness, compact status at
scale, and an alert-volume policy.
